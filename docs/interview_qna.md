# 面试专项题库

## 1. AI 效能研发题

### Q1：这个项目为什么属于 AI 效能，而不是普通 AI Demo？

答：它解决的是研发流程里的真实低效环节：CI 失败后开发者需要翻日志、查历史经验和重复排障。项目不是单纯聊天，而是把 CI 日志转成结构化诊断结果，并结合 RAG、工具上下文和评测指标，能嵌入研发平台形成效率闭环。

### Q2：如何衡量它是否真的提升效能？

答：分两层衡量。离线层看 schema 有效率、错误类型准确率、引用命中率和关键词覆盖率；线上层看 helpful rate、建议采纳率、平均排障时间变化、同类失败重复率下降和人工纠正率。

### Q3：产品化落地的第一步是什么？

答：先接入真实 CI 失败事件，比如 GitLab webhook 或 Job API，自动拉取失败 trace，做脱敏和关键行提取，然后把诊断结果评论到 PR 或发送到 IM。这个动作风险较低，用户反馈也容易收集。

### Q4：如何避免 AI 建议影响研发安全？

答：当前默认只分析和建议，不自动改代码、不自动重跑 pipeline。后续动作按风险分级：评论 PR 可以默认开启，创建 issue 需要项目授权，重跑 pipeline 和自动修复 MR 必须人工确认。

### Q5：这个项目怎么和研发效能平台结合？

答：可以作为平台的一个诊断服务。上游接 CI 平台、代码仓库和用户系统；中间做日志分析、知识检索、工具上下文；下游输出到 PR、IM、issue、Dashboard 和评测系统。

## 2. Python 后端深挖题

### Q1：为什么用 FastAPI？

答：FastAPI 适合这类 typed API 服务。它能基于 Pydantic 自动完成请求校验、响应模型、OpenAPI 文档生成；异步路由也适合 LLM/RAG/GitLab API 这种 I/O 密集型场景。

### Q2：Pydantic 在项目里解决了什么问题？

答：它同时保护两个边界：用户请求边界和模型输出边界。请求边界校验 log_text、project_name 等字段；模型输出边界校验 error_type、confidence、suggestions、references，避免非法 JSON 或缺字段结果进入下游。

### Q3：为什么 LLM 输出还要二次校验？

答：LLM 是概率模型，Prompt 约束不能保证 100% 合法输出。后端必须 `json.loads` 加 Pydantic 校验，把不可控自然语言转成可信结构；失败时返回格式异常或 fallback，而不是透传给调用方。

### Q4：异步调用的意义是什么？

答：LLM、GitLab API 和外部检索都属于 I/O 等待。使用 async 路由和异步 client 可以避免阻塞事件循环，在并发请求下更稳定。即使 Demo 规模小，也体现了服务化设计意识。

### Q5：异常分层怎么设计？

答：底层 SDK 异常不能直接暴露。项目把上游超时映射为 `LLMTimeoutError`，格式问题映射为 `LLMResponseFormatError`，其他上游故障映射为 `LLMServiceError`，router 再转换为 504 或 502。

### Q6：fallback 的价值是什么？

答：当 LLM 不可用或输出不合法时，规则 fallback 能保证服务仍返回一个可用的基础诊断结果。它不追求很智能，但能降低线上空响应和完全失败的概率。

## 3. RAG 专项题

### Q1：为什么要做 RAG？

答：直接问模型容易给通用建议，不一定符合团队内部 CI 规范。RAG 把故障手册、FAQ、历史 case 检索出来放进上下文，让回答更贴近团队经验，也能提供可追溯引用。

### Q2：RAG 的核心链路是什么？

答：日志文本进入 retriever，生成 embedding，通过 FAISS 检索 top-k 知识片段；这些片段进入 Prompt，模型基于日志和知识片段生成诊断；后端用真实 top-k 结果回填 references。

### Q3：为什么 references 不让模型自己生成？

答：模型可能编造引用或返回缺字段引用，导致不可追溯和 schema 校验失败。references 由后端检索结果决定，可以保证引用真实，也方便统计 reference hit rate。

### Q4：如何提升 RAG 效果？

答：可以从四个方向优化：知识库内容更结构化；query 侧做日志关键行提取；检索侧加入 reranker 和 score threshold；评测侧用 expected_reference_titles 监控命中率。

### Q5：RAG 和微调怎么选？

答：团队知识和故障手册经常变化，优先 RAG，因为更新知识库比重新训练更轻。微调适合稳定风格、固定分类或特定输出习惯，但不适合承载频繁变化的私有知识。

## 4. Tool Calling 专项题

### Q1：RAG 和 Tool Calling 的区别？

答：RAG 查的是知识资料，解决“模型不知道团队经验”的问题；Tool Calling 查的是系统状态或执行动作，解决“模型不能访问外部系统”的问题。本项目里 RAG 查故障手册，工具上下文查历史失败和 pipeline 信息。

### Q2：为什么当前先做规则版工具，而不是模型自主 tool calling？

答：规则版更稳定、可控、容易调试，适合项目早期。日志里出现固定关键词时调用对应工具，不需要模型判断是否调用。后续可以把工具注册成标准 function calling，让模型在受控范围内选择。

### Q3：Tool Calling 生产化最大的风险是什么？

答：风险在动作权限和错误动作。读取类工具风险较低，写入类工具必须授权和审计。自动评论、创建 issue、重跑 pipeline、提交 MR 应该分级控制，并保留人工确认。

### Q4：这个项目有哪些工具可以继续扩展？

答：可以扩展读取 `requirements.txt`、读取测试报告、查询 GitLab MR、查询最近失败记录、查询 runner 状态、创建 issue、评论 PR、推荐 owner 等工具。

## 5. 评测专项题

### Q1：为什么需要评测？

答：AI 项目不能只看 demo 返回一次结果。评测能把输出质量拆成结构合法性、分类准确性、检索命中和建议覆盖，帮助判断问题来自模型、Prompt、检索还是数据。

### Q2：当前评测指标有什么局限？

答：关键词覆盖率比较粗糙，不能完全代表建议质量；error_type accuracy 依赖人工标注；reference hit rate 只看标题命中，不能判断文档内容是否真的支撑结论。后续需要人工评分和线上反馈。

### Q3：如何设计更好的评测集？

答：覆盖不同错误类型、不同语言栈、长日志、噪声日志、多个错误共存、知识库无答案、敏感信息场景。每条样例标注 error_type、关键原因、期望建议、期望引用和是否允许 unknown。

### Q4：模型升级如何回归？

答：固定 eval_cases，每次改模型、Prompt、知识库或 retriever 后跑回归，比较 schema valid、error_type accuracy、reference hit 和 keyword score。如果指标下降，需要定位是哪条链路变化造成。

## 6. 项目优缺点

### 优点

- 场景真实，贴近研发效能。
- 从 LLM API 扩展到 RAG、工具上下文和 GitLab 接入。
- 有 Pydantic 结构化校验，输出可集成。
- 有评测脚本，能讲清楚质量闭环。
- 有 trace_id、fallback、脱敏等生产化意识。

### 缺点

- 真实 CI 平台接入还处于雏形。
- 工具调用目前偏规则版和 mock。
- 评测样例规模有限。
- 缺少完整鉴权、审计存储、Dashboard 和用户反馈接口。
- 测试覆盖还需要补齐。

## 8. 其他问题
### Q1. 为什么不用纯 LLM？

答： 纯 LLM 能做初步分析，但在企业研发场景里有两个问题：第一是缺少内部知识，比如构建规范、故障手册、历史案例；第二是容易泛化和幻觉。
所以我引入 RAG，把内部知识作为上下文输入，同时返回 references，让结论可追溯。

### Q2. RAG 在这个项目里解决什么问题？

答： RAG 主要解决静态知识检索问题。CI 故障分析需要参考故障手册、构建 FAQ、历史 case 等内部资料。
通过 embedding 和 FAISS 检索，把相关知识片段注入 Prompt，可以让模型从“泛泛建议”变成“基于团队经验的排查建议”。

### Q3. Tool Context 和 RAG 有什么区别？

答： RAG 查的是静态知识，比如文档、FAQ、历史经验；Tool Context 查的是动态系统上下文，比如 pipeline 阶段、job 状态、runner、branch、commit、历史失败次数。
两者结合后，模型既有经验知识，也有当前运行上下文。

### Q4. 为什么用 FAISS？

答： 当前项目是小规模知识库场景，FAISS 本地检索足够轻量，便于快速验证 embedding + Top-K 检索流程。
如果后续进入多项目、多租户、权限隔离和增量更新场景，可以迁移到 pgvector、Milvus 或 OpenSearch 等方案。

### Q5. 为什么要 Pydantic 校验 LLM 输出？

高级回答：
模型输出不能直接信任。即使 Prompt 要求 JSON，仍可能出现字段缺失、类型不一致、枚举值不稳定等问题。
Pydantic 校验可以保证输出结构符合下游系统要求，比如 error_type、confidence、references 都是固定格式，避免模型不稳定影响接口稳定性。

### Q6. 如何控制幻觉？

高级回答：

我从四层控制：Prompt 约束只能基于日志、知识片段和工具结果回答；
输出必须带 references；对模型结果做 Pydantic 校验；
评测集中记录 hallucination case，并反向优化 Prompt、知识库和检索策略。

### Q7. RAG 检索不准怎么办？

高级回答：

我会先看 Top-K 命中情况和 reference hit rate。
如果检索不准，可能是知识库缺失、chunk 切片不合理、embedding 模型不适合，或者 query 里噪声太多。
优化方式包括清洗日志关键行、调整 chunk、增加 metadata、混合关键词检索，以及替换更适合中英文/代码日志场景的 embedding 模型。

### Q8. 如何做评测？

高级回答：

我把评测拆成四层：结构层看 schema valid rate；分类层看 error_type accuracy；检索层看 Top-K reference hit rate；业务层看建议可执行性和幻觉率。
这样可以区分问题到底出在检索、生成、结构化输出，还是业务建议质量上。

### Q9. 模型超时怎么办？

高级回答：

LLM 是外部不稳定依赖，所以我会加 timeout、有限重试和降级。超时后可以返回规则分析结果，或者返回 RAG 检索结果并提示 AI 分析暂不可用，而不是让接口一直阻塞。

### Q10. 如何接入真实 GitLab？

高级回答：

我会单独抽象 GitLabClient，封装 job、pipeline、trace、commit 等 API。
拿到 trace 后不会直接送给模型，而是先做关键行提取、日志裁剪和敏感信息脱敏，再结合 stage、branch、commit_sha 等构造成 CIContext，
最后进入 RAG + Tool + LLM 分析链路。

### Q11. 如何控制成本？

高级回答：

主要从五个方面控制：日志关键行提取，避免完整 trace 进入 Prompt；
RAG top-k 控制；相同日志 hash 缓存结果；简单错误用规则或小模型；复杂场景才调用更强模型。同时记录 prompt 长度、模型调用次数、重试次数和降级率。

### Q12. 这个项目怎么产品化？

高级回答：

我会把它做成研发效能平台的 AI 诊断模块。
入口可以接 CI 失败页面、IM 通知和工单系统。
平台层面要补权限校验、敏感信息脱敏、审计日志、用户反馈和评测闭环。后续可以扩展到测试失败、发布失败、质量门禁失败等场景。
